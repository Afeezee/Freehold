# The S3 driver — Cloudflare R2, Backblaze B2, MinIO, AWS

One driver covers every S3-compatible endpoint. SigV4 signing is implemented
in the standard library (`hmac`, `hashlib`), so Freehold's only third-party
dependency is still `cryptography` — no boto3.

## Why this driver exists

To find out whether the storage abstraction was real or wishful. The rule was
that adding a second backend must not require touching `freehold/core`. It
didn't: the driver is `put`, `get`, `list`, `delete`, plus its own private
usage counter. The engine cannot tell it apart from GitHub, and a test asserts
the driver imports nothing from core except the interface and the error types.

If you drop GitHub entirely, nothing in the core changes — that was the point.

## Setup

### Cloudflare R2

Create a bucket, then an R2 API token (Object Read & Write). The endpoint is
`https://<account-id>.r2.cloudflarestorage.com` and the region is `auto`.

```bash
export FREEHOLD_S3_ACCESS_KEY_ID=...
export FREEHOLD_S3_SECRET_ACCESS_KEY=...

python -m freehold.cli backend add r2 s3 \
    endpoint=https://<account-id>.r2.cloudflarestorage.com \
    bucket=freehold region=auto
```

R2's free tier is ~10 GB stored with **no egress charge**, which makes it a
good restore target.

### Backblaze B2

Create a bucket and an application key, then use the S3-compatible endpoint
shown in the bucket details (`https://s3.us-west-004.backblazeb2.com` or
similar). The region is embedded in that hostname and must match.

```bash
python -m freehold.cli backend add b2 s3 \
    endpoint=https://s3.us-west-004.backblazeb2.com \
    bucket=freehold region=us-west-004
```

B2's free tier is ~10 GB stored, with free egress up to 3x the stored volume
per month.

### Options

| option | default | meaning |
|---|---|---|
| `endpoint` | — | S3 endpoint URL |
| `bucket` | — | bucket name (create it yourself) |
| `region` | `auto` | must match the endpoint for B2 and AWS |
| `prefix` | `freehold` | key prefix inside the bucket |
| `quota` | 10 GiB | free allowance to meter against, for warnings |
| `key_env` / `secret_env` | `FREEHOLD_S3_ACCESS_KEY_ID` / `..._SECRET_ACCESS_KEY` | where to read credentials |
| `access_key` / `secret_key` | — | inline credentials; stored in the manifest, so prefer the env vars |

## Layout and locations

```
bucket/freehold/3f/3f9a…       key = <prefix>/<first 2 of blob id>/<blob id>
```

A location is `bucket/key`. Keys are content-addressed and blinded, so a `PUT`
of the same chunk is idempotent, and the bucket reveals neither file names nor
plaintext hashes.

## Failure behaviour

- **401/403** (revoked or wrong credentials) → `BackendUnavailable`. The engine
  marks it unreachable for the run; a mirrored restore still succeeds from the
  other backend.
- **429** → `BackendUnavailable` immediately, so the engine degrades rather
  than hammering a rate-limited endpoint.
- **500/502/503/504 and connection errors** → retried with exponential backoff
  before being treated as unavailable.
- **404** → `ChunkNotFound`, naming the location.
- **Quota** — the driver counts the bytes it writes and warns from 80% of
  `quota`, then on every write past it. It does not stop: unlike GitHub LFS,
  going over costs money rather than failing, and that is the user's call to
  make. The warnings surface on backup output and in `backend info`.

## What is tested

Everything below runs against a local S3 server over real HTTP, which verifies
every SigV4 signature by recomputing it from the request as received — so a
driver that signed the wrong canonical request, or misreported its payload
hash, would fail rather than quietly pass against a mock.

- SigV4 matches **AWS's published `GET Object` test vector** exactly, which
  validates the signing formula itself rather than two halves of a test
  agreeing with each other.
- Byte-identical backup and restore; incremental sends only changed chunks.
- `list` across a server that pages two keys at a time; `delete` idempotency.
- Three consecutive 503s are retried and the backup still completes.
- Revoked credentials mid-life degrade to the mirror instead of failing.
- Uploads overlap under 8 workers and are strictly serial under `--workers 1`.
- The bucket holds no plaintext, no file names, and no plaintext hashes.

**Not yet run against real R2 or B2.** The signing is validated against AWS's
own vector and the whole path is exercised over real HTTP, so the remaining
risk is endpoint-specific quirks — B2's region handling and R2's token scopes
are the likely candidates. `tools/live_github_test.py` is the model for a live
S3 test if you want one; it needs a bucket and a key pair.
